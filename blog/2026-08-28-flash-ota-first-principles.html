I want to understand OTA from the bottom of the stack

I have used firmware tools for years. I want to know what they are actually doing.

A work-in-public note · Flash memory · ESP32 · OTA

There is a particular kind of technical knowledge that looks like understanding until you try to explain it without the tool that normally hides it from you.

“Flash the firmware.” “Install the bootloader.” “Do an OTA update.” These commands are wonderfully useful—and wonderfully good at hiding the machine underneath them.

So I am taking a step backward. Before I build a sophisticated OTA system, I want to understand the physical and software layers that make the simple command possible.

Start with the question: what does “programming flash” mean?

A binary file on my laptop is just a sequence of bytes. An ESP32 eventually executes instructions represented by those bytes. Between those two facts is an entire stack: a host tool, a transport, a flash controller, flash cells, a boot process, an address map, and software that interprets the resulting memory.

I don't want to memorize that stack as a diagram. I want to be able to reconstruct it from first principles.

The experiment I want to build

The first milestone is deliberately primitive: build a tiny flash programmer with my own hands. Not because it will compete with esptool, but because a deliberately bad tool makes the hidden steps visible.

The progression I have in mind is:

  1. Understand what a flash cell stores physically.
  2. Understand why flash has page-program and erase operations.
  3. Build a toy memory device and programmer model.
  4. Observe the difference between an address, a byte, a page, and an erase block.
  5. Move from the toy model to real external flash.
  6. Only then examine how a microcontroller boots from flash.
  7. Finally, reconstruct OTA as a controlled change to what the boot process considers executable.

Why OTA suddenly becomes interesting

Once the physical memory model is clear, OTA stops looking like magic networking infrastructure. It becomes a reliability problem around state transitions.

A device is running version A. Somewhere there is version B. The device must receive B, store it, verify it, decide whether B is trustworthy, boot it, and retain a way to recover if something goes wrong.

The interesting question isn't “how do I download a firmware image?” It is “how does a machine safely change the program it depends on while that program is currently running?”

The rule for this series

I am going to write these notes as experiments rather than tutorials. When I discover that I have been carrying a fuzzy mental model, I want the mistake to remain visible. When an abstraction saves me from understanding something, I want to peel it back at least once.

The destination is not a collection of OTA recipes. The destination is a mental model strong enough that the recipes become obvious.
